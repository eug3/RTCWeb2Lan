# 架构决策记录

## 已确认的约束（来自需求方）

1. **PC 端浏览器**为目标平台，不覆盖移动端 Safari。
2. **内网 web 零改造**：它就是一个普通网站，不需要任何隧道相关代码。
3. **域名与端口不变**：用户访问的 URL 与其看到的 URL 全程不变，内网 IP 不得出现在地址栏或页面可见 URL 中。
4. **P2P 不中转**：稳态流量不经过公网 VPS。
5. **公网只有一个静态初始化页**，用户只需访问一次；公网侧无服务端逻辑。

## 由此推出的必然结论

### 结论 1：Service Worker 是必需件，不是可选项

要让「内网 web 零改造」+「URL 不变」+「P2P」同时成立，浏览器必须能在**用户看不到的层面**替换请求的实际目的地。
浏览器中唯一具备该能力的内置机制是 Service Worker（拦截 fetch 并自行构造 Response）。

反过来：只要接受「流量过 VPS」，就可以用纯反向代理，完全不需要 SW。需求方明确选择了 P2P，因此 SW 路线成立。

### 结论 2：「只访问一次」的准确含义

SW 注册后持久存在，但会被以下情况清空：

- 无痕/隐私窗口（每次关闭即清空）
- 浏览器清理站点数据
- 磁盘压力下 Chrome 的自动清理
- 换设备、换浏览器

因此工程上应表述为「**每个浏览器 profile 只需访问一次**」，初始化页必须可重复访问且幂等。

### 结论 3：WebRTC DataChannel 不等于 TCP

DataChannel 基于 SCTP，面向**消息**且有单条消息大小上限；而 HTTP 需要**有序可靠字节流**。若要把 DataChannel 当作 overlay 的承载通道，必须自行实现：

- 分片与重组（含乱序与丢包重传策略）
- 流控与背压
- 连接建立/关闭的语义映射

这是方案 X 与 Z 工作量的主要来源，也是官方 easytier-js 选择 WebSocket 承载的原因。

### 结论 4：HTTPS 与首次加载

SW 仅在 **HTTPS（或 localhost）** 下可用。所以初始化页与内网域名都必须走 HTTPS，证书问题（自签/内网 CA）需在实现阶段单独处理。

## 待决策（阻塞项）

**初始化页建立链路时，peers 是否只能接受 WebSocket 地址？**

- 若**是** → 浏览器接入 overlay 的这一跳仍经过固定节点，做不到浏览器与内网严格直连。可将「P2P 不中转」解释为「稳态业务流量不过 VPS」。
- 若**否**，或接受自研 → 需实现浏览器直连内网 Agent（每台目标机一个 Agent）+ TCP-over-DataChannel 语义层。

## 与官方 easytier-js 的关系

- 上游已有 runtime / browser / cloudflare 三个包，但**均未发布到 npm**（实测 404），须 vendor 源码构建。
- @easytier/browser 的公开面是 **TCP client**：connectTcp(addr) -> {read, write, shutdownWrite, close}，正好对应本项目 OverlayTransport 的契约。
- 上游未提供 Service Worker / URL 寻址层，这正是本项目的增量价值所在。
## 决策已闭合（2026-10-21）

**允许信令经公网，数据面 P2P 直连。** 公网服务只负责「发现」—— 即信令与协调；
链路建立后，业务数据不经过公网。

This is exactly why EasyTier is in the picture：它的 overlay 会在节点之间自行打洞/直连，
公网节点只承担发现与（必要时）打洞协助。

### 基于源码核实的关键事实

阅读 `easytier-js/runtime/src/websocket-host.ts` 得到（非推测）：

- 暴露 `start_tunnel_connect(url)` / `take_tunnel_connect`：内网侧可以把一条 WebSocket
  **抽象为一条隧道（tunnel）** 接入 overlay。
- 隧道句柄可参与 `start_tunnel_send` / `start_tunnel_receive`，即通用的双向字节通道。
- `try_packet_write` 对隧道句柄返回 0（成功），说明隧道可承载通用数据。
- 因此：**WebSocket 是建链与发现的载体，不是数据面的必经中继**。
  overlay 打通后，EasyTier 节点间走自身 P2P 链路。

### 由此确定的实现路径

1. 公网：静态初始化页，用 WebSocket 作为「发现/信令」通道。
2. 浏览器：加载 EasyTier WASM，成为 overlay 的一个节点。
3. SW：把页面请求通过 `connectTcp(ip:port)` 送入 overlay，响应原路回灌。
4. 内网 web：零改造。

**注意**：`@easytier/browser` 的 `connectTcp` 目标是 overlay 内的 IPv4 地址，
因此 SW 的 `OverlayTransport` 只需接上它即可，无需自研 TCP-over-SCTP 语义层。
## 最终方案：自研 WebRTC DataChannel（C 方案）

由于官方 `easytier-js/runtime/src/config.ts` 中 `disable_p2p = true` 与
`peers must contain at least one WebSocket URL` 是**无条件写死**的，
官方 WASM 版在浏览器内不具备 P2P 能力，故放弃复用其数据面。

### 数据路径

```
页面 fetch(/api/x)                      ← URL 不变
  → SW 拦截（host/前缀规则）
  → HTTP/1.1 编码
  → MessagePort → 页面
  → RtcOverlayTransport.connect(authority)
  → DataChannel（P2P，直连内网 Agent）
  → 内网 Agent → 127.0.0.1:port → 内网 web（零改造）
  → 反向往回 → HttpResponseParser → Response
```

### 已实现并测试

| 模块 | 职责 | 测试 |
| --- | --- | --- |
| `src/signaling.ts` | 信令消息协议（仅控制面） | — |
| `src/datachannel-framing.ts` | 分片/组帧（10 字节头，5 种帧类型） | 9 |
| `src/rtc-transport.ts` | 单通道多路复用 → OverlayTransport | 8 |
| `src/data-plane.ts` | 页面侧数据面（含背压重试） | 4 |
| `src/port-transport.ts` | SW 侧 MessagePort 适配 | — |
| `src/router.ts` | URL 保持不变的 host/前缀路由 | 10 |

| 背压回归 | write 返回 0 不得当作错误 | 2 |

合计 45 个测试通过。浏览器 e2e 已验证 SW → MessagePort → 数据面 → Response 全链路，
且 `resUrl` 与 `location.href` 全程无内网 IP。

### 为什么不复用 EasyTier 的 TCP 栈

DataChannel 本身有序可靠，**不需要重写 TCP**。自研部分仅为：分片重组 + 多路复用 + 背压。
EasyTier 的价值退化为「内网节点间组网」，浏览器接入不走它。

### 尚未实现（下一步）

- RTCPeerConnection 握手（offer/answer/ICE）
- ICE 失败时的 TURN 兜底（**必需**，见下）
- 内网 Agent 端（接收 DataChannel，转发到 127.0.0.1:port）
- 信令中转服务（WebSocket 转发，可复用现有公网节点）

### 已知风险

1. **打洞不保证成功**：对称型 NAT 下 P2P 大概率失败。若不做 TURN 兜底，
   「不中转」会变成「不工作」。TURN 只在打洞失败时使用。
2. **每次刷新需重新握手**：WebRTC 连接绑定页面 JS 环境。可选优化：常驻
   SharedWorker 维持连接，实现浏览器内多标签复用。
3. **SW 与 WASM 生命周期**：SW 空闲会被回收，故数据面必须放在页面侧。

### 砍掉的设计（过度设计）

| 砍掉 | 原设计 | 为什么多余 |
| --- | --- | --- |
| `datachannel-framing.ts` | 10 字节帧头 + 5 种帧类型 | 每请求独立通道天然隔离，不需要流 ID |
| `StreamAssembler` | 流重组 | DataChannel 有序可靠，无需重排 |
| `rtc-transport.ts` 多路复用 | 单通道多流 | 每请求开一条通道即可 |

净减少约 400 行代码。

### 新设计

```
一次 HTTP 请求 = 一条 DataChannel
  客户端：分片(16KiB-1) 发送 → 空消息表示结束
  服务端：分片回复        → 空消息表示结束
```

传输契约从「连接+读写流」简化为一次 `exchange(authority, requestBytes) -> responseBytes`。

### 借鉴的关键点

1. **空消息作为 EOF**：`send(nil)` 表示消息结束，无需长度前缀。
2. **Agent 侧管理 Cookie**：SW 无法操作 Cookie，必须在内网 Agent 用 cookiejar 处理。
3. **重定向改写**：3xx 的 Location 由 Agent 转成绝对地址回传。
4. **每次请求新开 DataChannel**：隔离性免费获得。

### 保留的自有优势

- **多 host / 前缀路由**（`router.ts`）：参考实现只支持单一 host。
- **URL 全程不变**：浏览器 e2e 已验证 `resUrl` 与 `location.href` 无内网 IP。
- **34 个单元测试**。

### 本次重构中修掉的 bug

1. **Event 错误不可读**：`String(event.error)` 输出 `[object Object]`，真实错误被吞。
   已改为按 `error` / `message` / `type` 逐层提取。
2. **测试 stub 事件不分类型**：`message` 事件被投递给 `error` 监听器，造成假报错。
   已改为按类型分发。

### 仍未实现

- **内网 Agent（Go + pion/webrtc）**：接收 DataChannel，用 `http.ReadRequest` 解析，
  经 cookiejar + ReverseProxy 转发到 `127.0.0.1:port`，`resp.Write` 回传。
- **信令服务器**：WebSocket 房间转发 SDP/ICE。
- **STUN / TURN 部署**：国内不可用公共 STUN，须自建。

## 最终实现：单通道多路复用（2026-10-23）

「一请求一 DataChannel」在真实环境里几乎不可用。生产实测：25 次 API 调用中 **0 次**走成隧道，
其余全部静默回落兜底。两个独立原因：

### 原因 1：DCEP 握手经常完不成

每条新通道都要一次 DCEP 握手。Chrome 与 pion 的组合下这一步经常超时
（`channel open timed out`），请求只能重试到放弃。SCTP 流重置还会污染同一关联上的后续流。

换成**一条通道承载所有交换**后，这两个问题一起消失：

```
帧格式：kind(1) + stream(4) + payload(<= 16KiB-5)
  kind: DATA / END / ABORT
  END  替代原先的「空消息作 EOF」
```

实测：30 并发 × 3 轮的楔形回归测试从 **18 秒且全失败** 变成 **0.18 秒零失败**。

### 原因 2：Agent 的 cookie jar 从未被查询

`http.ReadRequest` 产生的 `req.URL` 是**相对 URL**（只有 path，host 在 `req.Host`），
而 `http.Client` 用 `jar.Cookies(req.URL)` 查 cookie。URL 里没有 host，查找永远落空，
于是 Agent 不管存了什么会话都表现为未登录。诊断日志可以一眼看出：

```
POST /api/auth/login    url=/api/auth/login    jarCookies=0
GET  /api/auth/session  url=/api/auth/session  jarCookies=0
```

修法是给请求补上绝对 URL（scheme/host 只用于 jar 查找，`Transport` 之后仍会改写成真实 target）。

### 结论

这两处修完之后，业务接口才真正走 P2P：**30/30 命中，p50 31ms**（此前 0/25、p50 78ms、最大 3080ms）。

同时也说明「认证必须绕开隧道」这个早期结论是错的——Agent 可以自己登录并持有会话，
认证走隧道反而才能让业务流量走 P2P。详见 README「认证与会话」。

## 已知硬限制（来自 Service Worker API，非实现问题）

- **不支持 WebSocket 代理**：内网 web 若依赖 WS 实时推送，用不了。
- **内网页面自身不能再注册 SW**：SW 槽位被占用。
- **HTTP 语义差异**：禁止的头（Forbidden headers）无法伪造。
