# 如何测试

## 方式一：一键本地栈（假内网服务，最稳）

```bash
pnpm run dev:stack
```

它会拉起：演示用内网服务、`fdn`（资产 + 信令 + 兜底）、`tunnelagent`、vite dev server，并打印访问地址。

打开输出的 URL，等连接页自动跳到站点，然后：

| 验证点 | 期望 |
| --- | --- |
| 响应 URL | **不出现内网 IP** |
| 返回内容 | 含 `HELLO-FROM-INTRANET-SERVICE` |
| `x-w2l` 响应头 | `tunnel` |

## 方式二：对接真实内网服务

前置：本机已能访问目标内网服务（例如 `curl <内网IP>:<端口>/health` 通）。

```bash
# 终端 1：公网边缘（资产 + 信令 + 兜底）
./.dev-bin/fdn -addr 127.0.0.1:8787

# 终端 2：内网代理
./.dev-bin/tunnelagent \
    -signal ws://127.0.0.1:8787/__lan/ws \
    -room real \
    -target http://<内网IP>:<端口>

# 终端 3：页面
pnpm --dir fdn/web dev
```

打开：

```
http://127.0.0.1:5273/?signal=ws%3A%2F%2F127.0.0.1%3A8787%2F__lan%2Fws&room=real
```

## 方式三：换任意内网服务

只改 `tunnelagent` 的 `-target`（或用 `-routes` 配多站点），其余不变。页面地址相应改 `&room=...`。

## 用命令行直接验收

```bash
pnpm test          # 前端单测
pnpm run test:go   # Go 单测（转发、信令、多路复用、兜底）
pnpm run check     # 两者一起
```

生产环境验收，看响应头的 `x-w2l`：

| `x-w2l` | 含义 |
| --- | --- |
| `tunnel` | 完整走隧道（P2P 直连）——**这才是成功** |
| `401-fallback` | 隧道送到了，但上游要求登录，SW 重放走源站 |
| `fallback` | 交换失败，直接走源站 |

> 不要用「有没有 `server` 头」判断：上游可能自己发 `server`，源站也会盖一个，两个方向都不可靠。

## 测试时要盯住的三件事

1. **`x-w2l` 是不是 `tunnel`** —— 是 `401-fallback` 说明认证没走隧道，见 README「认证与会话」。
2. **响应 URL 里有没有内网 IP** —— 有就是地址泄露，属于失败。
3. **内容是不是真实服务返回的** —— 用 `build_id` 这类会变的字段证明，不要只看 200。

## 已知会失败的情况

| 现象 | 原因 |
| --- | --- |
| 打不开任何页面 | SW 未激活；先访问一次连接页 |
| 请求超时 504 | `tunnelagent` 没在跑，或 `-room` 与 `config.json` 不一致 |
| 全部是 `401-fallback` | 认证没走隧道（`neverTunnel` 应为空），或 Agent 重启后 jar 丢失，重新登录一次 |
| 返回 404 | 请求路径与 `routes.yaml` 的 target 不匹配 |
| 页面空白 / JS 报错 | 内网页面依赖 WebSocket，SW 无法代理（会回落，不经 P2P） |
| 隧道时通时断 | `tunnelagent` 与 `fdn` 版本不一致——两端协议耦合，必须同时升级 |
